# 两个项目的后端负责人审查与面试追问

> 评审日期：2026-10-23；版本：v1.0。  
> 目标：快速形成可信的简历项目，理解 Agent 核心，不涉及硬件。  
> 范围：本地方案审查、上游公开文档与竞争方案核查。没有安装或运行两个候选项目，没有测得性能提升，也没有验证真实用户付费意愿。

## 1. 先给不讨好的结论

**两个项目都具备实现路径，但原方案都不能直接照着开工。技术可实现，不等于产品有需求，更不等于做出来就有招聘竞争力。**

如果我是后端技术负责人：

| 我看到的项目 | 第一印象 | 最初的怀疑 | 什么能让我认可 |
|---|---|---|---|
| A：Evidence-to-Test | 题目具体，演示有记忆点 | 是否只是让模型写 Playwright？是否把测试通过误当成安全证明？ | 冻结合同、真实缺陷检测、可靠执行、可追溯结果，以及对模板基线的增益 |
| B：REA Tool Router | 与 AI 工具基础设施接近，有系统工程空间 | 是否只是搜索工具名再转发？现成代理或手选工具是否已经足够？ | 正确处理状态/权限/协议故障，且实测任务收益超过最强简单基线 |

我不会因为用了 REA、MCP、Agent、多代理或向量数据库就给高评价。我会看你能否解释：问题为何成立，哪些代码是你写的，正确性如何定义，系统出错以后会怎样。

**按“后端/AI 基础设施求职”优先考察 B；按“Agent 应用、开发工具、测试智能化”优先考察 A。两者都必须先通过小规模验证关卡。** 这是岗位匹配判断，不是已证明 B 比 A 强。

对于传统 Java/Go 业务后端岗位，这两个项目只能补充工程经历，不能代替数据库事务、索引、网络、并发、业务建模等基础。不要为了补关键词强行加入 Kafka、Redis、Kubernetes。

## 2. 对上一版建议的纠正

1. 撤回 A 77 分、B 73 分的精确评分：它们是主观印象，不是测量结果，不能支持可靠决策。
2. 撤回“几周兼职即可完成整套方案”的承诺：原范围包含的安全、协议、评测工作被明显低估。
3. 不再把“新组合”当作“没人做过”：通用测试 Agent、证据判定、工具检索都有现成工作。
4. 不再把所有计划功能都视为 MVP：先证明一条闭环，再增加 Agent 与可视化。
5. 不再把“能生成代码”和“能可靠验证”混为一谈，也不把“目录更小”和“总成本更低”混为一谈。
6. 优先级从“演示吸引力”调整为“你的目标岗位、可验证贡献和投入上限”。因此不再无条件推荐 A。

## 3. 竞争与需求：哪些事实成立，哪些仍是假设

### 3.1 A 的竞争边界

Playwright 官方已有 planner、generator、healer。因此“自动规划、生成并修复测试”本身不是差异化。[官方 Test Agents](https://playwright.dev/docs/test-agents)

CounterProof 已公开围绕 PR 主张、回放、Oracle 和证据回执的设计；其 REA 相关 #172 是 Draft 实验，不能说它已经成熟实现了我们的 Electron 测试闭环，也不能再说“证据与显式未知”是独创。[CounterProof](https://github.com/hippoley/CounterProof)、[实验 PR #172](https://github.com/hippoley/CounterProof/pull/172)

我们的待验证差异应缩为：**一类 Electron IPC 文件边界合同，能够从静态线索绑定到真实 Renderer 调用，产出对 unsafe/fixed 两个版本有效的普通回归测试。**

需求仍未被验证：开发者是否真有足够多这样的测试需要自动化？维护绑定的成本是否低于手写？必须找实际开发者试用或记录真实历史修复案例，不能靠自造 fixture 回答市场问题。

### 3.2 B 的竞争边界

现成项目已经提供延迟发现与代理调用；不能把“四个元工具 + 搜索”写成原创核心。[mcp-tool-search](https://github.com/KGT24k/mcp-tool-search)、[lazy-tool](https://github.com/mcp-shark/lazy-tool)

REA 上游已提交 compact 默认展示的变更。因此旧 issue 的大目录测量只能作为历史动机，不能冒充今天本机、本模型的成本。[compact 变更](https://github.com/morluto/rea/commit/aa51e4343963fdd0b97ec2ebdc3c41579fd9cb38)、[历史问题 #5861](https://github.com/morluto/rea/issues/5861)

我们的待验证差异应缩为：**针对少数真实工作流，维护 Evidence 依赖与状态，在不越权、不丢失结果语义的前提下，证明路由优于现成搜索或静态小工具集。**

最危险的反例：如果目标用户只分析 JS，手动固定十几个工具就够，那么一个动态 Router 的额外复杂度可能不值。必须允许实验得到“不值得单独做产品”的结论。

## 4. A 的关键不足与修订决定

这里的“阻断”表示必须在方案或实现中先解决，不代表已经发生线上事故。

| 级别 | 原方案问题 | 为什么会被追问 | v0.3 的修正 |
|---|---|---|---|
| 阻断 | 临时目录、浏览器请求拦截被写成沙箱 | Electron 主进程仍有宿主权限 | 首版仅受控、已审阅 fixture；不声称可安全运行未知安装包 |
| 阻断 | 未复现等于 refuted | 有限输入不能证伪广泛的存在性命题 | 只判定本次用例，使用 policy_satisfied_for_case 等受限结论 |
| 阻断 | 风险复现和回归测试极性不清 | 漏洞复现脚本可能修复后才变红 | 安全断言必须 unsafe 红、fixed 绿；环境失败不能绿 |
| 阻断 | Healer 可改启动参数 | 不改断言也能通过换目标、配置制造假绿 | 冻结目标、环境、参数、策略和测试数据 |
| 阻断 | 主进程注入被当作 Renderer 可达性 | 测试可能自己绕过安全边界 | 从真实暴露的 Renderer API 进入；观察不代替触发 |
| 重要 | 断言变异或坏 channel 被当安全 mutation | 基础设施出错不等于检测到安全缺陷 | 对被测程序注入语义缺陷，按正确断言失败计数 |
| 重要 | 只测自己写的简单样例 | 容易把模板适配当泛化能力 | 按实现家族留出；真实独立目标是后续外部验证 |
| 重要 | 缺少执行生命周期定义 | 崩溃、取消、重复运行会污染结果 | 明确 run/attempt、持久状态、进程归属与恢复规则 |

Playwright 仍将 Electron 支持标为实验性；打包配置也可能影响启动。因此“所有 Electron 应用都能测”不成立。[Electron 自动化文档](https://playwright.dev/docs/api/class-electron)

### A 应该演示什么

1. 准备一个应用策略允许目录和一个策略外目录；两者都在测试自建目录中。策略外放本次生成的随机 canary，不读用户真实文件。
2. 同一份冻结的安全合同测试 unsafe 与 fixed：合法读取都成功；非法读取在 unsafe 泄漏、fixed 拒绝。
3. 安全回归测试在 unsafe 上失败，在 fixed 上通过；报告清楚列出本次运行条件，不写“应用绝对安全”。
4. 再故意让入口缺失或运行超时：系统报告无结论或失败，不生成假绿结果。
5. 展示 Agent 试图修改 Oracle/环境时被代码拒绝；展示与无 LLM 模板的对比。

这比展示十张生成截图、长规划文本或多个角色互相聊天更能说明工程能力。

## 5. B 的关键不足与修订决定

| 级别 | 原方案问题 | 为什么会被追问 | v0.3 的修正 |
|---|---|---|---|
| 阻断 | 先删除所有 unavailable 工具再补依赖 | 需要前置步骤才能启用的目标会被误删 | 分清可立即执行、可补齐、不可用；执行前重检 |
| 阻断 | route token 被当用户授权 | 模型可以给自己选工具，参数还能换目标 | 路由票据只表明选择快照；授权由独立可信策略判断 |
| 阻断 | compact schema 被当完整合同 | 代理预检可能遗漏约束 | 标明展示合同与上游验证的边界；不宣称等价 |
| 阻断 | 任意状态变化让整条路由失效 | 前置步骤产出 Evidence 就会使后续票据自失效 | 区分连接/目标/策略代际与正常资源账本更新 |
| 重要 | 只算首次工具列表 Token | 新增搜索轮次与返回 schema 会占后续历史 | 统计整段任务实际输入、输出、缓存、耗时与成功率 |
| 重要 | 固定 top-k 被叫最小可执行链 | 贪心检索不保证最优，跨参数依赖可能未满足 | 声明启发式可行计划；真实参数与资源引用验证 |
| 重要 | 通用 call 仍被说成透明 MCP | 宿主看到的是元工具，原注解和 UI 行为会变化 | 公开支持范围，首版不代理任意危险或交互工具 |
| 重要 | 超时统一重试 | 上游可能已完成，重试会重复副作用 | 保留 outcome_unknown，按工具语义决定恢复，默认不重放未知调用 |

上游强调完整发现合同、验证与 Evidence 语义不能在优化中被削弱。独立代理可以提供自己的选择接口，但不能声称替代了 REA 的完整协议合同。[上游设计约束 #723](https://github.com/morluto/rea/issues/723)

### B 应该演示什么

1. 同一个真实 JS 分析任务，比较 compact 直连、人工静态小集合、通用搜索代理、你的路由器。
2. 缺少应用分析 Evidence 时，正确安排生产步骤；已有可用 Evidence 时，复用而不是重复分析。
3. 在检索后、调用前改变目录或断开连接：拒绝陈旧引用，不拿上一连接的 ID 继续执行。
4. 在相同票据下替换目标路径：独立策略阻止越界，而不是因为“模型说允许”就调用。
5. 打开原始测量表：可能省 Token 但更慢，可能某些任务失败；完整展示，别只选最佳案例。

## 6. 面试官会怎样追问 A

| 问题 | 回答中必须拿得出的证据 |
|---|---|
| 有源码为什么非要经过 REA，直接 AST 或读代码不行吗？ | Evidence 在引用、覆盖范围、关联结构上的具体收益，以及接入与版本维护成本；若没收益就不强行依赖 |
| 我手写测试半小时，你到底省了什么？ | 同任务的模板/人工流程对照，人工修改次数与总耗时；没有增益就诚实缩小定位 |
| 这是 Agent 还是固定工作流？ | 哪一步有受限自主选择，观察如何改变下一动作，何时停止；固定部分明确叫编译器 |
| 谁定义正确答案？ | 人或 fixture 给出的合同、批准记录、不可变摘要；不能由生成者自己定义所有成功条件 |
| 没有读到文件就安全了吗？ | 单用例结论、未覆盖输入、环境限制，负面观察不扩大为全局安全 |
| 怎么证明是 Renderer 调用而非你注入主进程实现的？ | 真实入口、窗口身份、输入和返回观察；静态关联不冒充完整运行因果链 |
| 你怎样防止自愈把测试修没了？ | 类型化修改白名单、固定断言/启动环境、被拒绝的修改案例 |
| 把程序弄崩也能让测试红，凭什么叫检出缺陷？ | 有效 mutant 定义、正向检查、精确失败断言；启动失败单列 |
| 运行中被取消或电脑重启怎么办？ | 持久状态、interrupted、所属进程清理、重新运行的新 attempt，不伪称恰好一次 |
| REA 和程序都升级后，证据怎么对应？ | 源证据与执行版本分别标识，适配器版本、契约测试与不兼容错误 |
| 为什么在你的样例上有效，在我的应用上不行？ | 支持矩阵、留出实现家族、失败样本；尚无外部验证必须直说 |
| 导出的测试脱离你的系统还能运行吗？ | 普通 Playwright 测试、最小依赖、manifest 和一条复现命令 |
| 哪一部分真是你实现的？ | 合同/DSL、编译器、判定器、执行管理与评测；REA 分析和 Playwright 执行明确归上游 |

## 7. 面试官会怎样追问 B

| 问题 | 回答中必须拿得出的证据 |
|---|---|
| 为什么不直接手选十几个工具？ | 和静态小集合的同任务对照；若无增益就不能宣称必须动态路由 |
| 为什么不用现成的 Tool Search？ | 在相同输入、预算、模型下，状态依赖或失败恢复的具体改善，不只是名字不同 |
| 查到目标工具却没有前置 Evidence 怎么办？ | 真实 producer/consumer 引用合同与依赖计划，不是仅返回一堆工具名 |
| availability=false 是不能用还是暂时不能用？ | 不可用原因分类、可补齐条件、调用前重检；未知原因不猜测 |
| 模型自己得到一个路由票据就有权限了吗？ | 不会；可信策略独立判断，绑定路径/目标/允许能力；annotations 不是安全边界 |
| catalog 没变，但权限或连接变了呢？ | schema digest 之外的代际与策略版本；连接内 Evidence ID 不能跨连接直接复用 |
| 你的 schema 校验为什么不如上游严格？ | 展示投影可能省略约束；代理校验定位于早期报错，上游才是最终权威 |
| 把 schema 塞回工具结果，不还是占上下文？ | 逐轮实际使用量、历史累积、缓存计费；不能拿首次传输量替代总费用 |
| 请求超时后再发一次会怎样？ | outcome_unknown、实际副作用分类、恢复检查；不声称通用 exactly-once |
| 你如何证明 Evidence 没有被改坏？ | 同一捕获响应的转发契约测试；跨运行比较需区分动态 ID/时间，不删除限制和未知 |
| 20 条任务少失败一次能证明提升 3% 吗？ | 不能；20 条的一例就是 5 个百分点，报告计数、区间和有限外推 |
| 工具更新、缓存损坏、并发和取消怎么测？ | 固定版本测试夹具、目录刷新与过期拒绝、请求关联、队列上限及故障注入记录 |

## 8. 两者共同缺少的“后端含金量”如何补齐

不是加技术栈，而是完成少量真实的可靠性责任：

- **身份与一致性**：输入、目标、版本、策略、运行结果不能串；缓存命中也不能跨边界。
- **状态机**：区分未开始、执行中、取消中、完成、失败、结果未知；不能一个 error 字符串包办。
- **资源上限**：限制并发、队列、单次输出、日志/trace、执行时间；达到上限返回明确错误，不默默截断事实。
- **失败恢复**：中断后的事实先保留，不盲目续跑有副作用的动作；取消请求成功不等于目标已停止。
- **可观测性**：通过 run/request/attempt ID 串起过程；能从失败样本定位到阶段与原因。
- **安全与隐私**：源码、路径、日志可能敏感；发给远端模型前说明内容与范围，默认使用公开 fixture；报告不记录密钥。
- **可复现**：版本锁定、环境说明、固定种子或明确随机字段、基线脚本、原始结果与失败案例齐全。

先单机、单用户、一个受支持平台即可。高并发架构、多租户与分布式调度没有真实需求时应明确不做。

## 9. 开源二次开发怎样避免被认为只是换皮

README 单独设置“基于什么、我新增什么、哪些仍不支持”三栏；保留许可证与上游归属。

| 层次 | 可以复用 | 必须展示的个人工作 |
|---|---|---|
| A | REA 静态分析、Playwright 执行、已有测试框架的 CLI 基础 | 类型化合同与绑定、确定性安全判定、目标变异评测、执行恢复 |
| B | 现成代理的连接与工具发现、搜索组件、SDK | REA 资源依赖适配、调用前策略/状态校验、异常语义、强基线测量 |

不需要为了“个人贡献比例”重写成熟组件。真正重要的是你负责的关键行为能从设计、代码、测试到结果形成证据链。

目前复用仓库只是候选，尚未完成安装、代码质量、依赖风险与许可证适配检查。不要把“README 能做”当作“接入一定只要一天”。不合适时只复用库，或提交一个清晰的上游改进，也比换个名字 fork 整仓好。

## 10. 快速求职的投入策略与停止条件

**不建议同时启动两个项目。先按岗位选一个，用验证关卡避免把数周投入给一个并不成立的卖点。**

- A：先用 12–20 小时做手工闭环。冻结同一安全测试，区分 unsafe/fixed；跑不通就停止扩展 Agent。
- B：先用 20–30 小时做离线/小规模真实对照。必须包含静态小工具集；如果增益不成立，收缩为适配器、评测工具或上游贡献。
- A 的扎实版估计 100–160 小时；B 估计 85–130 小时，均以熟悉 TypeScript 的单人开发为前提，不含任意应用强隔离、多平台、多租户。
- 这是设计拆分估计，不是交付保证。若只有两周业余时间，完成一项可信的小改进，比宣称完成整个平台更现实。

继续投入的条件不是“Demo 漂亮”，而是：真实闭环能运行、主要错误分支可解释、个人贡献清楚、至少一个对照指标有价值。结果为负也应公开；不能改评测题来保住选题。

## 11. 简历上可以怎样写，不能怎样写

以下只可在实际完成后使用；尚未完成的项目不能照抄为既成成果。

**A：**“基于 REA 与 Playwright 开发 Electron 文件访问边界回归工具；实现不可变验证合同、受限测试绑定与确定性结果判定，通过 unsafe/fixed 配对和目标程序变异验证测试有效性，支持超时/取消与证据追溯。”

**B：**“基于开源 MCP 代理实现面向 REA 的状态感知工具调用层；实现 Evidence 依赖补齐、目录与会话失效处理、参数级调用策略和异常恢复，在固定任务集上对比 compact 直连、静态工具集与通用检索代理。”

后续仅填写真实测量值，并给分母、环境和基线。不写“零幻觉”“100% 安全”“首次提出”“工业级”“大幅提升”或继承自上游的虚构个人成果。

## 12. 最终评审意见

我愿意继续看这两个项目，但不会只凭方案给它们通过。

**A 的机会在“测试结论真的可信”；B 的机会在“工具调用真的可靠且有净收益”。最值得写进简历的，是你能现场解释并复现的一个难点，而不是整个方案里出现了多少新名词。**
